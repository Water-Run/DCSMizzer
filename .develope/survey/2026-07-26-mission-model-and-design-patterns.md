# DCSMizzer 任务模型与设计规律（2026-07-26）

> 历史测绘：数字、上游提交和能力状态已由 2026-07-27 可重现基线取代；本文只保留作方法与决策记录。

## 1. 文档用途

本文把
[903 个独立 MIZ 内容与 5 个独立 CMP](2026-07-26-miz-cmp-corpus-map.md)
的实际结构，归纳为未来 DCSMizzer 文档和工具应理解的任务模型。

结论分为两类：

- **观测事实**：从当前语料字段、数量和源码直接得到；
- **开发约束**：为避免破坏真实任务而推导的未来实现要求。

本文不定义最终 API，也不表示解析器、生成器或验证器已经实现。

## 2. 数据不是一个单表

真实任务至少是一个存档、多个 Lua 数据表、资源文件和引用关系共同组成的图：

```text
.miz (ZIP)
├─ mission
│  ├─ metadata / weather / options references
│  ├─ coalition
│  │  └─ side → country → category → group → unit
│  │                                  └─ route → waypoint → task
│  ├─ triggers / trigrules / goals / result
│  └─ resource and dictionary keys
├─ options
├─ warehouses
├─ l10n/<locale>/dictionary
├─ l10n/<locale>/mapResource
└─ referenced images / audio / Lua / kneeboard / DTC / track data

.cmp
└─ campaign
   └─ stage
      └─ mission reference → sibling .miz
```

因此“生成一个 Lua `mission` 表”不足以构成完整 `.miz`。反过来，一个 ZIP 能解压
也不足以证明内部引用、触发器和运行时行为有效。

## 3. 三层模型

### 3.1 存档层

存档层负责：

- 成员路径、大小、压缩、CRC、重复成员和编码；
- 核心表是否存在；
- 字典、资源映射与实际成员之间的引用；
- 安全限制，例如路径穿越、压缩炸弹和脚本不可执行。

真实语料证明这一层必须保留重复成员信息和未知文件。只把已知六个成员解压后重新
打包，会丢失 kneeboard、DTC、脚本、语音、轨迹和模块扩展。

### 3.2 原始 Lua 层

原始层应表达 Lua 表的实际键和值：

- 字符串键、数字键和表内裸标识符键；
- 稀疏数字索引；
- Unicode 键和值；
- 历史拼写与未知扩展字段；
- `nil`、布尔值、数值、字符串和嵌套表。

当前 pydcs 解析器对两个 Saved Games 任务的裸标识符键失败，说明原始层不能直接
等同于某个上游库的对象模型。

### 3.3 规范化语义层

规范化层可提供便于 Agent 使用的概念，例如：

- 地图、联盟、国家、组、单位、槽位、航路点、任务和目标；
- 冷启动/热启动/跑道起飞；
- 任务类型的跨语言语义；
- 资源、字典和触发器引用；
- 战役阶段与分数区间。

规范化必须是附加视图，而不是覆盖原始数据。每个规范化值都应能追溯：

- 原始键和值；
- 来源文件与任务格式版本；
- 使用的 DCS/数据版本；
- 是否经过别名、翻译或默认值推导。

## 4. `mission` 顶层

### 4.1 全部安装任务都出现的字段组

648 个安装任务全部包含以下重要顶层字段：

- 格式与时序：`version`、`start_time`；
- 场景：`theatre`、`weather`、`map`；
- 阵营：`coalition`、`coalitions`；
- 触发与结果：`trig`、`triggers`、`trigrules`、`goals`、`result`；
- 任务控制：`failures`、`forcedOptions`、`groundControl`、`currentKey`；
- 简报引用：`descriptionText`、`descriptionBlueTask`、
  `descriptionRedTask`、`pictureFileNameB`、`pictureFileNameR`。

字段“存在”不代表其表非空。例如 Saved Games 样本的 `trigrules` 和 `goals` 可以
存在但没有条目。

### 4.2 条件出现的字段

| 字段 | 安装任务出现数 | 兼容性含义 |
|---|---:|---|
| `maxDictId` | 647 | 唯一 v6 任务缺失 |
| `sortie` | 647 | 同上 |
| `date` | 637 | 不能设为无条件必需 |
| `requiredModules` | 625 | 当前主流模块声明 |
| `pictureFileNameN` | 614 | 中立方简报图片并非普遍存在 |
| `descriptionNeutralsTask` | 583 | 中立方任务说明可省略 |
| `pictureFileNameServer` | 244 | 服务器图片 |
| `drawings` | 185 | 地图绘制 |
| `needModules` | 23 | 历史/替代模块字段 |
| `usedModules` | 17 | 历史/替代模块字段 |
| `ext_loader` | 16 | 扩展加载相关 |
| `initScriptFile` | 11 | 初始化脚本文件 |
| `customFormations` | 5 | 自定义编队 |
| `initScript` | 2 | 内联初始化脚本 |

开发约束：

- 读取时接受字段缺失和历史替代写法；
- 生成时选择一个经过当前 DCS 验证的规范版本；
- 未知字段默认保留，不得因模式未声明而删除；
- `initScript*` 和其他脚本只作为不可信数据处理。

## 5. 联盟到单位的数据图

实际层级为：

```text
mission.coalition
└─ blue | red | neutrals
   └─ country[n]
      ├─ plane.group[n]
      ├─ helicopter.group[n]
      ├─ vehicle.group[n]
      ├─ ship.group[n]
      └─ static.group[n]
```

`blue` 与 `red` 在全部安装任务出现；`neutrals` 只在 476/648 个任务出现。
国家通常由数字索引表表达。国家、联盟和类别都不能从组名推断。

组与单位的 ID 是跨触发器、航路点、链接静态物和脚本引用的基础。未来生成器必须在
全任务范围分配稳定、无冲突的 `groupId`/`unitId`，并在重新编号时更新所有引用。

## 6. 组模型

### 6.1 共同字段

移动组通常具有：

- `groupId`、`name`、`x`、`y`、`start_time`；
- `units`；
- `route`；
- `hidden`、`lateActivation`、规划器/MFD 可见性；
- 类别相关的 `task`、`tasks`、`taskSelected`；
- 概率、通信或可控状态等可选字段。

静态组的组织方式不同：常见 `heading`、`dead`、`linkOffset`，没有飞行组式的通信、
任务和激活语义。

### 6.2 固定翼与直升机

全部 8,188 个固定翼组具有频率、调制、通信、任务、路线和单位。实际还观察到：

| 字段 | 固定翼组 | 直升机组 |
|---|---:|---:|
| `dynSpawnTemplate` | 4,832 | 631 |
| `lateActivation`（字段存在） | 4,178 | 449 |
| `hiddenOnPlanner` | 2,072 | 152 |
| `hiddenOnMFD` | 1,619 | 130 |
| `DTC` | 87 | 0 |

`uncontrolled` 和 `uncontrollable` 两种键都在真实语料出现。它们不能在没有版本和
语义证据时按拼写纠错合并。

### 6.3 地面与舰船

地面组具有位置、路线、可见性和单位；部分组没有任务字段。实际观察到：

- 11,241 个地面组中，1,904 个含 `lateActivation` 字段；
- 4,487 个地面组含 `uncontrollable`；
- 93 个地面组含 `manualHeading`；
- 舰船组可有频率/调制、路线、late activation 和隐藏属性。

道路、越野、铁路、海上路线和编队不能共享一个没有约束的通用移动模板。

## 7. 单位模型

### 7.1 共同标识

各类别单位都至少依赖：

- 精确 DCS `type` 字符串；
- `unitId` 与 `name`；
- `x`、`y`、`heading`；
- 类别相关的技能、载荷、外观和可控性。

自然语言机型名不能直接写入 `type`。类型、国家、任务能力和模块要求必须来自当前
安装数据或经过版本标记的导出。

### 7.2 飞行单位

11,325 个固定翼单位和 1,489 个直升机单位都具有高度、速度、航向、呼号、载荷和
机载编号。重要可选结构包括：

- `payload.pylons`：具体挂点与 CLSID；
- `AddPropAircraft`：机型专用属性；
- `parking`、`parking_id`、`parking_landing*`；
- `Radio`；
- `datalinks`；
- `DTC`/`dataCartridge`；
- `hardpoint_racks`；
- `livery_id`。

本轮只证明这些字段真实存在，并统计了挂载字符串；没有证明每个 CLSID 对当前机型、
挂点、任务和年代仍合法。生成前还必须查本机数据库或经过验证的导出。

### 7.3 地面、舰船与静态物

地面单位普遍具有 `playerCanDrive`；还观察到：

- `transportable`；
- `coldAtStart`；
- `AddPropVehicle`；
- 弹药和列车 `wagons` 等少量扩展。

静态单位的真实字段包括 `shape_name`、`rate`、`canCargo`、`mass`、`offsets`、
效果字段和 heliport 通信字段。历史模式还使用拼写 `lenght`、`lenghtRope`。
未来序列化器不能把这些键自动改成英文拼写正确但 DCS 不认识的名称。

## 8. 坐标与位置语义

现有参考与真实任务共同确认：

| 上下文 | 北向 | 东向 | 高度 |
|---|---|---|---|
| `.miz` 单位/航路点 | `x` | `y` | `alt` |
| pydcs `Point` | `x` | `y` | — |
| DCS/MOOSE/BriefingRoom Vec3 | `x` | `z` | `y` |

WGS84 经纬度不能直接写入任务 `x`/`y`。地图投影、地形边界、机场位置、跑道和停机位
必须绑定具体地图版本。

位置一致性至少包括：

- 组位置与首单位位置；
- 航路点位置、高度类型和动作；
- 机场/helipad ID；
- 停机位及落地停机位 ID；
- 绑定单位的 `linkUnit` 与偏移；
- 地形可达性、道路/水域/跑道约束。

本轮没有运行地形碰撞或 DCS 编辑器验证，因此只形成数据约束，未证明任意生成坐标
可用。

## 9. 航路点与起飞状态

飞行航路点的稳定字段包括：

- `x`、`y`、`alt`、`alt_type`；
- `speed`、`speed_locked`；
- `ETA`、`ETA_locked`；
- `type`、`action`；
- `task`；
- 可选 `airdromeId`、`helipadId`、`linkUnit`、`properties`、`name`。

地面和舰船航路点复用部分字段，但动作、路线可达性和编队约束不同。静态物在任务表
中也带位置型路线点，不能因此当作可移动 AI。

真实起飞/开始状态由多字段联合表达：

| 用户概念 | 观测到的主要数据 |
|---|---|
| 冷启动 | `From Parking`、机场/停机位、组开始时间、单位属性 |
| 热启动 | `From Parking Hot`、机场/停机位 |
| 跑道起飞 | `From Runway`、`airdromeId` |
| 空中开始 | 航路点类型/动作、高度、速度与位置 |
| 延迟出现 | `lateActivation` 和触发器 |
| 停机待命 AI | `uncontrolled` 与触发/启动动作 |

未来自然语言接口必须保留用户指定的启动状态，不能因为某个机场没有已验证停机位就
静默替换成空中开始。

## 10. 任务与动作

任务存在多个层级：

1. 组级角色 `group.task`；
2. 组级任务集合或 triggered actions；
3. 航路点 `task.params.tasks`；
4. `WrappedAction` 内的命令；
5. 触发规则激活或下发的任务。

安装任务中最常见的航路点任务是 `WrappedAction`，其次包括目标交战、受控任务、
盘旋、攻击组、火力点和轰炸。说明完整生成器不能只写航路点坐标；通信、ROE、反应、
任务启停和交战约束常被包在高级航路点动作中。

组级角色还存在多语言值。建议未来内部模型同时保存：

- `raw_task`：原始字符串；
- `normalized_role`：有证据的规范语义；
- `normalization_source`：语言/别名规则版本；
- `confidence`：明确映射或未知。

未知值应保持未知，不能用最接近的英文枚举强制替换。

## 11. 触发器、目标与结果

完整任务的行为不只在单位和航路点中：

- `triggers` 可包含区域；
- `trigrules` 组织条件与动作；
- `goals` 定义得分/目标；
- `result` 与触发器共同表达离线、红、蓝结果；
- 动作可激活组、设置旗标、显示文本/图片、播放声音、下发 AI 任务或运行脚本。

安装语料有 14,834 条规则、23,017 个条件和 31,739 个动作。官方战役子集只占
任务数量 22.2%，却贡献约 48% 的规则和约 89% 的目标。因此：

- QuickStart/训练样本适合起飞、槽位、载荷和教学流程；
- 官方战役更适合成功/失败、节奏、资源与叙事编排；
- 两类样本不能用一个简单平均值合并成“典型任务”。

脚本类动作和初始化脚本必须视为不可信代码。静态分析器可以记录引用、大小、哈希和
触发位置，但默认不能执行。

## 12. 字典、简报与资源

任务正文通常通过键间接引用 `l10n/<locale>/dictionary`；图片、音频和脚本通过
`mapResource` 关联到存档成员。由此产生的完整性规则包括：

- `mission` 中的字典键应能在所选 locale 的字典中解析；
- `mapResource` 的资源名应对应实际、规范化后仍位于存档内的成员；
- 不同 locale 可能不完整，必须定义回退顺序；
- 资源文件名大小写在 Windows 上可能不敏感，但 ZIP 和跨平台工具不能依赖这一点；
- 未引用资源与缺失资源应分别报告；
- 重新打包不得擅自删除未知资源。

本轮只统计简报字段字符数，没有提交或复述任何受版权保护的简报、图片、声音和战役
描述。

## 13. 天气、时间与时代

天气至少包括：

- 风层；
- 云与预设；
- 能见度；
- 雾；
- 降水；
- 季节/温度；
- 气旋或其他扩展。

真实语料同时存在无云预设、多个普通/雨天预设、雾和降水。未来输入模型应允许用户
指定天气，也应区分“用户明确指定”“按地区/季节生成”“使用 DCS 默认”。

任务日期与年代不是同一概念。默认日期、编辑器遗留日期和故事年代可能不同。时代
一致性必须综合验证：

- 用户指定日期/年代；
- 地图及地图版本；
- 国家/联盟；
- 单位服役期；
- 武器可用期；
- 涂装、机场和战役背景。

`.develope/reference/` 的年代数据只能在其来源版本内作为候选，不能跳过本机验证。

## 14. 仓库与补给

所有安装任务都有 `warehouses`，但规模从空表到大量机场/对象条目不等。仓库模型
涉及：

- 机场和对象 ID；
- 燃料种类与数量；
- 武器库存；
- 航空器库存；
- 供应者关系；
- 运作级别。

任务能够加载不代表玩家所需弹药、燃油和机体在仓库中可用。未来验证器必须在用户
要求启用有限库存时检查任务载荷与仓库库存的一致性。

## 15. 战役推进模型

本机 5 个独立 `.cmp` 展示两种结构：

1. 44 个阶段各引用一个任务，区间为 0–100；
2. 25 个阶段各引用四个任务，以 0–50、51–100 等分数区间选择候选。

战役层只提供阶段、分数区间、起始阶段、任务引用、必要模块和本地化媒体。每个
`.miz` 内的触发器、目标和结果仍决定实际得分与成功/失败条件。

未来战役验证必须跨文件检查：

- `.cmp` 的每个相对 `file` 是否存在；
- 阶段编号是否连续或有意稀疏；
- 区间是否重叠、留空或覆盖期望分数；
- `startStage` 是否存在；
- `necessaryUnits` 与任务 `requiredModules` 是否相容；
- 任务结果是否能产生推进所需分数；
- 图片和描述的本地化引用是否存在。

本轮 144 个任务引用全部能相对 `.cmp` 目录解析。没有在 DCS 中执行战役推进，
所以分数选择的运行时行为仍标记为未验证。

## 16. 从自然语言到任务的建议数据流

测绘结果支持以下未来流程，但本轮没有实现：

```text
用户场景约束
  → 明确化且不丢失的场景规格
  → 按版本查询地图/机场/单位/武器/任务能力
  → 生成空间、联盟、编组、航路和目标计划
  → 生成触发器、结果、简报、资源和仓库
  → 序列化为带 provenance 的 MIZ/CMP
  → 存档/模式/引用/场景约束验证
  → 可用时进入 DCS 运行时验证
```

每一箭头都需要可报告的失败，而不是静默替换。例如用户要求特定武器但本机数据无法
证明挂点兼容时，应报告限制并请求选择，不得换成“相近武器”。

## 17. 最低保真约束

未来生成或修改任务时，至少要保持：

- 用户指定的时代、联盟、模块、地图、玩家数、天气、启动状态、时长和输出约束；
- 精确 DCS 类型、ID、坐标、停机位、任务能力、挂点和 CLSID；
- 全任务 ID 唯一和引用一致；
- 字典/资源映射/存档成员闭包；
- 原始未知字段和 Unicode 值；
- 触发器、目标、成功/失败与战役区间之间的可达关系；
- 可复现输入、随机种子和数据版本；
- 生成内容与安装、上游、参考任务的物理隔离。

## 18. 尚待补证据

在把本文转成产品规范前仍需：

- 用当前 DCS 编辑器创建并重新保存最小任务，比较 v23 的规范输出；
- 用 DCS 本体加载代表性冷启动、热启动、跑道、空中、多玩家和战役任务；
- 从本机数据库验证机场/停机位、武器挂点和任务能力；
- 补齐本机未安装地图与模块的合法样本；
- 验证触发器、脚本、仓库和战役分数的运行时行为；
- 为解析器建立合法 Lua 数据子集与安全边界。

这些工作应先通过
[Docs/Tools 开发源图](2026-07-26-docs-tools-source-map.md) 的验收门，再进入
产品目录。
