# Low-level MIZ build specification

This is the **normative construction contract**. Read it when authoring,
auditing, or diagnosing a build spec; it is not part of the default discovery
path. Start with [quickstart.md](quickstart.md), and use
[mission-format.md](mission-format.md) only when raw MIZ/Lua structure is the
question.

`build-miz` accepts one complete UTF-8 JSON document with schema:

```text
dcsmizzer.miz-build-spec/v1
```

The input is limited to 16 MiB and 128 JSON object/array levels. Both limits
are checked before recursive validation or output publication. Keep bulk
briefing media outside the JSON and declare it through `resources`, where the
separate archive policy applies.

It is a serialization contract, not a scenario language. The caller supplies
the full DCS data tables and all exact identifiers. The builder never invents
defaults, chooses variants, resolves compatibility, or changes the design.

## Top-level object

Only these keys are accepted:

| Key | Required | Meaning |
|---|---:|---|
| `schema` | yes | Exactly `dcsmizzer.miz-build-spec/v1` |
| `mission` | yes | Complete Lua `mission` table encoded as JSON, except fields generated by optional `logic` |
| `options` | yes | Complete Lua `options` table |
| `warehouses` | yes | Complete Lua `warehouses` table |
| `dictionary` | yes | Flat string-to-string localization table |
| `mapResource` | yes | Flat string-to-string resource mapping table |
| `resources` | no | Binary files to package; default empty array |
| `expect` | no | Finite post-build scenario contract; default empty object |
| `logic` | no | Finite trigger/goal source with schema `dcsmizzer.miz-logic/v1` |
| `seed` | no | String or integer recorded for provenance |
| `provenance` | no | Caller-authored JSON object recording evidence |
| `quality` | no | Exactly `{"profile":"technical_fixture"}` or `{"profile":"complete_scenario"}`; default is `technical_fixture` |

Unknown keys, duplicate JSON keys, non-finite numbers, and unsupported value
types are rejected. JSON `null` is forbidden in the five serialized core
tables. Nonserialized metadata and contract sections have their own field
rules; in particular, the two nullable `expect.roles` fields documented below
are not emitted into Lua.

`mission.version` must be numeric and `mission.theatre` must be a nonempty
single-line string. The builder writes `mission.theatre` into the plaintext
`theatre` archive member.

`warehouses` must contain both an `airports` table and a `warehouses` table,
even when either registry is empty.

## Quality profiles

Use `technical_fixture` only for bounded format experiments and regression
fixtures. It preserves the original low-level behavior: implemented structural
errors fail, while structural warnings and contract-coverage warnings remain
review items.

Use this profile for a user-facing mission:

```json
{
  "quality": {
    "profile": "complete_scenario"
  }
}
```

`complete_scenario` adds both an input gate and a post-build quality gate. The
input must contain:

- a deterministic `seed`;
- a nonempty `provenance` object whose top-level keys are nonempty and whose
  top-level values are neither JSON `null` nor empty strings;
- a nonempty `expect` contract;
- at least one actual group and unit, including at least one `Player` or
  `Client` slot, plus a nonempty `expect.roles` manifest;
- finite `logic` compiler input with at least two trigger rules;
- at least one positive-score success goal and one negative-score failure goal;
- no positive and negative goal pair with identical condition sets;
- a valid calendar `mission.date`, `start_time` in `[0, 86400)`, a cloud table,
  and ground/2,000 m/8,000 m wind layers;
- the current observed runtime shell: `coalitions`, `currentKey`, `failures`,
  `forcedOptions`, `groundControl`, `map`, `maxDictId`,
  `pictureFileNameB`, and `pictureFileNameR`, plus complete blue/red
  coalition-side tables;
- `mission.requiredModules` as a table;
- current core options fields and no local audio-device identifiers;
- complete current-shape warehouse records for every airdrome ID used by a
  route;
- all complete-profile air-group, route, unit, payload, briefing, and task
  fields described below.

After read-back, every structural warning and every
`contract.coverage_warnings` item is fatal to the complete-profile quality
gate. In addition, every actual mission group must be bound exactly once by an
`expect.roles` record. A report is accepted only when
`validation.quality_gate_passed` and `validation.available_checks_passed` are
both true.

The profile name describes static authoring completeness. It does not imply
that DCS loaded the mission; `validation.runtime_valid` remains `null`.

`mission.start_time` is a time-of-day offset in seconds since midnight.
Group `start_time`, waypoint `ETA`, and `c_time_after` are a different domain:
elapsed seconds from mission start. Do not add the time-of-day value to them.
Every human flight must start at elapsed `0`.

## JSON-to-Lua mapping

| JSON | Lua |
|---|---|
| object | table with string keys |
| array | table with dense numeric keys starting at 1 |
| string | escaped UTF-8 string |
| integer/finite number | Lua number |
| boolean | Lua boolean |

An ordinary JSON array is correct for dense DCS arrays:

```json
{
  "units": [
    {"unitId": 1, "name": "Lead"},
    {"unitId": 2, "name": "Wingman"}
  ]
}
```

Use the exact `$fields` wrapper for sparse numeric or mixed-key Lua tables:

```json
{
  "pylons": {
    "$fields": [
      {
        "key": 1,
        "value": {
          "num": 1,
          "CLSID": "{EXACT-VERIFIED-CLSID}"
        }
      },
      {
        "key": 6,
        "value": {
          "num": 6,
          "CLSID": "{ANOTHER-EXACT-VERIFIED-CLSID}"
        }
      }
    ]
  }
}
```

`$fields` must be the object's only key. Each record must contain exactly
`key` and `value`; keys must be unique finite strings or numbers.

Do not use a JSON object with keys such as `"1"` when DCS expects numeric key
`1`; that would serialize a Lua string key. Known DCS sequence tables must use
the contiguous keys `1..N`, including countries, groups, units, route points,
task lists, trigger rules/conditions/actions, goals, and zones. Payload pylons
are the deliberate exception: their positive numeric keys may be sparse
because station numbers are not array positions. The gate also rejects
stringified numeric keys in an aircraft callsign table; use `$fields` for its
mixed numeric and string keys.

Omit a DCS field instead of writing JSON `null`. The builder deliberately does
not emit Lua `nil` table entries.

## Minimum authoring responsibilities

The format does not define a universal DCS schema. Author the full,
version-appropriate shape from current static and observed evidence. A typical
mission still needs:

- version, theatre, date, start time, and verified weather fields;
- coalition side/country/category/group/unit tables;
- exact country IDs, unit types, global IDs, names, coordinates, skills, and
  category-specific fields;
- complete group routes, waypoint actions, and nested task tables;
- exact payload, fuel, countermeasure, radio, and aircraft-specific settings;
- trigger zones plus either the finite `logic` source below or complete
  top-level trigger/goal/compiled-result tables;
- the current observed runtime shell described below, including coalition
  membership and briefing-picture tables even when their arrays are empty;
- briefing dictionary references and complete narrative;
- an explicit `mission.requiredModules` table, normally empty unless exact
  evidence establishes a required plugin ID;
- warehouses/options shapes appropriate to the installed version.

Do not treat an abbreviated documentation fragment as a DCS-ready template.
Use [evidence.md](evidence.md), [mission-format.md](mission-format.md), and
anonymous observed field-count/variant shapes for an exact caller-supplied
type/theatre filter. Resolve exact version-specific field names and shapes from
current public/static evidence or an independently inspected authorized
mission.

## Limited structural gate

The input spec is rejected before packaging when the finite structural pass
finds an error. It checks:

- coalition table and numeric country IDs;
- contiguous `1..N` keys and table items in known DCS sequence tables, while
  preserving sparse positive numeric pylon stations and the sparse global goal
  keys required in each side-specific compiled-result table;
- nonempty, globally unique group/unit IDs and names;
- nonempty group units and non-static routes;
- waypoint `x`, `y`, `type`, and `action`;
- standard plane/helicopter main-task display strings and a task table with
  nonempty `id` plus `params` on every air waypoint;
- unit type, coordinates, heading, applicable skill, and aircraft altitude;
- distinct `x/y/alt` positions for units in the same airborne-start group;
- pylon-table shape, unique stations, and nonempty CLSIDs;
- runway/parking-start destination references: exactly one positive numeric
  `airdromeId`, or `helipadId == linkUnit` resolving to a static/ship unit;
- exact first-waypoint air-start `type`/`action` pairing, same-coalition
  static/ship linkage, and ground-area starts that require no facility or
  parking reference;
- for airdrome parking starts, each unit's parking and duplicate occupancy;
- placement of mission logic at the top level rather than under `triggers`;
- trigger-rule/goal shape, compiled table linkage, and common
  group/unit/zone references;
- native MiG-29 GCI station activation, action parameters, and a recognized
  same-side compatible radar within the documented link range;
- present briefing keys resolving to dictionary strings.

A missing `parking_id` on a parking start is currently a warning. A clean
structural result still does not prove the full DCS schema or runtime validity.

With `complete_scenario`, the finite pass additionally requires:

- nonnegative integer `currentKey` and `maxDictId`;
- table-valued `failures`, `forcedOptions`, `pictureFileNameB`, and
  `pictureFileNameR`;
- finite `map.centerX`/`centerY` and positive `map.zoom`;
- dense integer country-ID membership arrays in `coalitions.blue` and
  `coalitions.red`, with every country used under the matching
  `coalition.<side>.country` present; `coalitions.neutrals` is checked when
  supplied or used;
- blue and red coalition sides with exact `name`, numeric
  `bullseye.x`/`y`, table-valued `nav_points`, and table-valued `country`;
  an authored neutral side is checked the same way;
- `groundControl.isPilotControlVehicles` as a boolean and
  `groundControl.roles` as a table containing the four observed role tables
  `artillery_commander`, `forward_observer`, `instructor`, and `observer`;
  each role contains table-valued `blue` and `red` subtables (empty tables are
  valid);
- all five briefing fields to be present and, because warnings are fatal,
  resolve to nonempty dictionary strings;
- `communication`, `frequency`, and `modulation` on every plane/helicopter
  group;
- numeric `alt`, `speed`, and `ETA`; nonempty `alt_type`, `type`, and `action`;
  and boolean `ETA_locked`/`speed_locked` on every air waypoint;
- both locks exactly true on the first plane/helicopter waypoint, and no later
  waypoint with both locks true. For a normal speed-controlled leg use
  `ETA_locked=false`/`speed_locked=true`; for a required arrival time use
  `ETA_locked=true`/`speed_locked=false`. Both false remains structurally
  accepted for observed special cases;
- for an airborne start with a first leg longer than one metre, lead-unit
  `heading` within five degrees of
  `atan2(second.y-first.y, second.x-first.x)`;
- group `start_time` equal to the first waypoint `ETA`;
- nonnegative route ETAs and group start times; when present,
  `lateActivation` must be a boolean, and each `Player`/`Client` group starts
  at elapsed `0` without late activation;
- nonnegative waypoint/unit speeds, positive speed for airborne starts, and
  positive speed on later non-landing waypoints. Parking/ground/runway first
  points, their units, and landing points may retain a zero planning speed;
- a landing point to use exactly `type="Land"` and `action="Landing"`, with
  either numeric `airdromeId` or the numeric `helipadId` plus `linkUnit` pair,
  but not both;
- every runway/parking first point to use that same exclusive airdrome or
  linked-facility reference form; a linked FARP/ship start may omit unit
  parking when the observed shape does, while a ground-area start needs
  neither form;
- aircraft/helicopter unit `alt`, `speed`, `alt_type`, `callsign`, and
  `onboard_num`;
- a payload table with a pylon table, numeric or numeric-string `fuel`, and
  numeric `chaff`, `flare`, and `gun`;
- an actionable nested combat task for every all-AI air group whose main task
  is one of the implemented combat families.

These runtime-shell fields were present with the stated shapes throughout the
accepted current official-mission core-shape sample. Requiring them prevents a
minimal serialization fixture from passing as a user mission. It still does
not prove that DCS accepts the authored values or that the list is a universal
DCS schema.

The route-lock rule was replayed read-only over all 648 installed official
missions: all 8,188 plane-route first points were double-locked; among 23,065
later plane points, 22,992 were speed-only, 55 ETA-only, 18 unlocked, and zero
were double-locked. The 1,055 helicopter routes showed the same zero
post-start double-lock result. Do not add a universal
`distance / ETA difference == speed` hard check: even official routes contain
leg timing differences caused by route and task semantics that this static
two-dimensional check cannot model.

The air-start heading rule was independently replayed over 920 calculable
airborne starts in 66 current official MiG-29 module missions: every lead
heading matched the first route leg within one degree. The complete gate uses
a five-degree tolerance. It does not apply this rule to parking/runway/ground
starts because those headings require facility or observed-mission evidence.

### Air-waypoint task semantics

For every plane/helicopter waypoint, the root task must be
`ComboTask` with a `params.tasks` table. Each direct child must have:

```text
id        nonempty string
params    table
number    positive integer
auto      boolean
enabled   boolean
```

In `complete_scenario`, `number` must also equal that child's numeric sequence
key; the mismatch is only a warning under `technical_fixture`.
`ControlledTask` is treated as a wrapper: `params.task` must contain its own
nonempty `id` and `params`, and supported nested combat tasks are checked
recursively without requiring the direct-wrapper fields again.

The implemented semantic checks are deliberately bounded:

| Task ID | Required semantics |
|---|---|
| `AttackGroup` | `weaponType` is a nonnegative integer. The complete profile also requires `groupId`, `groupAttack`, `attackQtyLimit`, positive `attackQty`, altitude/direction enable flags and numeric values, and a recognized `expend` value. A referenced target group must exist, be hostile, and not be static. |
| `AttackMapObject` | Requires numeric `x`/`y` and nonnegative-integer `weaponType`. The complete profile also requires altitude/direction fields and enable flags, positive `attackQty`, `attackQtyLimit`, `groupAttack`, and a recognized `expend` value. |
| `Bombing` | Requires numeric `x`, `y`, `altitude`, and `direction`; the corresponding enable flags; positive `attackQty`; nonempty `expend`; and nonnegative-integer `weaponType`. The complete profile also requires `attackQtyLimit` and `groupAttack`, and validates the `expend` value. |
| `BombingRunway` | Requires positive-integer `runwayId` and nonnegative-integer `weaponType`. The complete profile also requires altitude/direction fields and enable flags, positive `attackQty`, `attackQtyLimit`, `groupAttack`, and a recognized `expend` value. |
| `EngageTargets` | Requires a nonempty dense string `targetTypes` sequence and numeric `priority`. `maxDist` must be positive and paired with `maxDistEnabled`; if enabled, the distance must be present. |
| `EngageTargetsInZone` | Requires nonempty dense string `targetTypes`, numeric `x`/`y`, and positive `zoneRadius`; the complete profile also requires numeric `priority`. |
| `Escort` | Requires positive `engagementDistMax`, an existing different friendly plane `groupId` (never the source group), positive in-range `lastWptIndex`, a numeric `pos.x/y/z`, and nonempty dense string `targetTypes`. The complete profile also requires both last-waypoint flag fields. |

Optional fields recognized by these task families are type-checked when
present. This is not a universal task schema. For an all-AI combat group, the
complete profile also checks that a dense `ComboTask` route contains at least
one `enabled=true` task which passed its implemented semantic checks and is
compatible with the main task. Examples include `Escort` for an escort group,
`AttackGroup`/`AttackMapObject`/`Bombing` for ground attack, and
`BombingRunway` for runway attack.

For `complete_scenario`, attach `Bombing` to an ingress/attack waypoint near
its target, not to a distant departure point. The static gate rejects a
two-dimensional waypoint-to-target distance above 200 km. In the current
installed official sample, all 324 observed `Bombing` tasks were below 174 km
and the 95th percentile was about 57 km. This conservative ceiling detects a
gross activation error; it is not a terrain-path, AI-behavior, or weapon-range
proof.

## Finite trigger and goal compiler

Prefer top-level `logic` for the common condition/action families it supports.
When `logic` is present, omit `trigrules`, `trig`, `goals`, and `result` from
`mission`; supplying either representation at the same time is rejected. The
compiler writes those four fields separately at the correct mission level.
`mission.triggers` remains the trigger-zone table only.

The source must contain exactly:

```json
{
  "logic": {
    "schema": "dcsmizzer.miz-logic/v1",
    "trigger_rules": [
      {
        "kind": "once",
        "comment": "Authored mission deadline passed",
        "conditions": [
          {"predicate": "c_time_after", "seconds": 4200},
          {"predicate": "c_flag_is_false", "flag": 1}
        ],
        "actions": [
          {"predicate": "a_set_flag", "flag": 2}
        ]
      },
      {
        "kind": "once",
        "comment": "Strike package stopped",
        "conditions": [
          {"predicate": "c_unit_dead", "unit": 201},
          {"predicate": "c_unit_dead", "unit": 202},
          {"predicate": "c_flag_is_false", "flag": 2}
        ],
        "actions": [
          {"predicate": "a_set_flag", "flag": 1}
        ]
      }
    ],
    "goals": [
      {
        "side": "OFFLINE",
        "score": 100,
        "comment": "Interception succeeded",
        "conditions": [
          {"predicate": "c_flag_is_true", "flag": 1}
        ]
      },
      {
        "side": "OFFLINE",
        "score": -100,
        "comment": "Interception failed",
        "conditions": [
          {"predicate": "c_flag_is_true", "flag": 2}
        ]
      }
    ]
  }
}
```

Supported trigger `kind` values are:

```text
once
continuous
start
front
```

Only no-event rules are compiled. Supported conditions and their exact fields
are:

| Predicate | Required numeric fields |
|---|---|
| `c_time_after` | `seconds` |
| `c_flag_is_true` | `flag` |
| `c_flag_is_false` | `flag` |
| `c_flag_equals` | `flag`, `value` |
| `c_unit_dead` | `unit` |
| `c_group_dead` | `group` |
| `c_unit_in_zone` | `unit`, `zone` |
| `c_part_of_group_in_zone` | `group`, `zone` |

Supported actions are:

| Predicate | Required fields |
|---|---|
| `a_set_flag` | `flag` |
| `a_set_flag_value` | `flag`, `value` |
| `a_activate_group` | `group` |
| `a_out_text_delay` | `dictionary_key` (string), `seconds` (number), `clearview` (boolean), `start_delay` (number) |

Flags, group IDs, unit IDs, and zone IDs must be positive integers. Referenced
group/unit IDs must exist in the authored coalition, and a
`c_unit_in_zone` and `c_part_of_group_in_zone` zones must exist as numeric
`zoneId` under
`mission.triggers.zones`. Goal sides are `RED`, `BLUE`, or `OFFLINE`; goal
scores are integers from -100 to 100. Trigger rules, actions, goals, and goal
conditions are nonempty; only a `start` trigger may have no condition.
`c_part_of_group_in_zone` means **PART OF GROUP IN ZONE**: any part of the
group entering the zone satisfies it. It is not the unsupported
**ALL OF GROUP IN ZONE** predicate.
Compiled trigger tables use dense `1..N` keys. In the compiled result, each
side's `conditions`, `actions`, and `func` tables retain the global numeric key
of the corresponding entry in `mission.goals`; these side tables can therefore
be sparse. Structural validation requires the three exact key sets to match
the valid, nonempty goals for that side. An empty-rules goal remains included
in `result.total` and is an error, but does not require a compiled side key.

### Mutually exclusive terminal outcomes

Treat success and failure as terminal states, not independent milestones. For
one success flag `S` and failure flags `F1..Fn`, author the finite logic in this
order:

1. place every failure-writer rule before the success-writer rule;
2. add `c_flag_is_false(S)` to every failure writer;
3. add `c_flag_is_false(Fi)` for every failure flag to the success writer;
4. make the positive goal read `S` and each negative goal read its failure
   flag;
5. do not use `kind="start"` for any terminal writer, because startup
   functions compile into a separate execution phase;
6. do not reset a terminal flag or assign it any value other than true through
   `a_set_flag` or `a_set_flag_value` with `value=1`.

Under `complete_scenario`, the static gate requires these reciprocal false
guards and the failure-before-success order. A passing report records:

```text
generation.logic_compilation.terminal_outcome_dataflow.guard_order_contract_passed = true
generation.logic_compilation.terminal_outcome_dataflow.runtime_mutual_exclusion_proved = false
generation.logic_compilation.terminal_outcome_dataflow.temporal_reachability_proved = false
```

The first field proves only that the authored rules contain those conservative
guards and order, that terminal writers are not startup rules, and that no
supported finite action clears or assigns another value to a terminal flag. It
does not prove how DCS evaluates same-frame rules, that a terminal path is
reachable, or that runtime success/failure is mutually exclusive. Keep the
flags and writers distinct and retain runtime uncertainty.

`a_out_text_delay` compiles the same dictionary-backed action shape observed
in current real missions. `dictionary_key` must be a safe 1-128 character key
containing only letters, digits, `_`, `.`, `:`, `/`, or `-`; it must resolve to
a nonempty string in top-level `dictionary`. Both timing fields are
nonnegative. Example:

```json
{
  "predicate": "a_out_text_delay",
  "dictionary_key": "DictKey_GCI_Update_01",
  "seconds": 12,
  "clearview": false,
  "start_delay": 0
}
```

This can provide authored command-post updates, but it is not a replacement
for native MiG-29 GCI. Build the station, `ActivateGCI` waypoint task, and
compatible radar as documented in [mission-format.md](mission-format.md).

Conditions within one rule are joined with logical AND. Arbitrary Lua,
scripts, OR expressions, event triggers, sound/radio actions, coalition-
targeted messages, and other predicates are outside this finite compiler. Do
not encode them approximately; leave the requirement unresolved or supply
separately verified complete low-level DCS tables.

## Options, warehouses, and required modules

Do not author current core options or warehouse records from memory. Produce
bounded current-install templates:

```powershell
python Tools\dcsmizzer.py dcs-options-template `
  --dcs-root "D:\path\to\DCSWorld" `
  --player-name "DCSMizzer" `
  --full-sim

python Tools\dcsmizzer.py dcs-warehouse-template `
  --dcs-root "D:\path\to\DCSWorld" `
  --airdrome-id 7 `
  --airdrome-id 8 `
  --coalition NEUTRAL
```

Use the first report's `options` value and the second report's `warehouses`
value in the build spec. Record their relative source names and SHA-256 values
in `provenance`. The options command safely parses the installed data-only
Mission Editor default, gives `playerName` a deterministic caller-selected
value, blanks local audio-device fields, and changes only its documented
difficulty fields when `--full-sim` is selected.

The warehouse command accepts only caller-supplied numeric airdrome IDs.
Resolve those IDs first with an exact terrain-specific airbase query. It emits
numeric `$fields` keys and a complete unlimited-mode airport record using
verified current-install Mission Editor literals. It does not prove the ID,
initialize the runtime inventory registry, or infer the authored warehouse
coalition.

In `complete_scenario`, every numeric `airdromeId` used by any route must have
an airport entry containing the current 20-field warehouse shape. The
top-level `warehouses.warehouses` table must still exist even when empty.

`mission.requiredModules` is independent of the human-slot aircraft. Do not
infer a plugin ID from a player aircraft or module display name. Current
observed missions overwhelmingly use an empty table, so use:

```json
{
  "requiredModules": {}
}
```

unless exact version-matched evidence requires otherwise. A nonempty
complete-profile table may contain only exact plugin-ID string keys mapped to
the identical string value.

## Resources

Each resource record contains exactly:

```json
{
  "member": "l10n/DEFAULT/briefing-image.png",
  "source": "../assets/briefing-image.png"
}
```

- `member` is a safe relative POSIX archive path.
- `source` is resolved relative to the spec file unless absolute.
- Member names must be unique and cannot replace a core member or `theatre`.
- The output path cannot overwrite the spec or a resource input.
- Every `mapResource` value must resolve to a packaged archive member, either
  directly or under `l10n/DEFAULT/`.
- Build and verification hash every packaged resource and require its bytes to
  equal the source file named by the spec.

Prefer relative resource paths so the build remains reproducible. Do not
package copyrighted source-mission assets.

## Scenario contract

`expect` supports exact top-level values:

```json
{
  "theatre": "EXACT_INTERNAL_THEATRE",
  "mission_version": 23
}
```

`minimum` and `exact` accept the following counter facts. Each maps selected
string keys to nonnegative integer counts:

```text
groups
units
human_slots
unit_types
slots_by_type
payload_clsids
waypoint_actions
waypoint_task_ids
group_tasks
start_modes
trigger_condition_predicates
trigger_action_predicates
goal_predicates
```

They also accept these scalar facts with a nonnegative integer:

```text
pylon_assignments
trigger_rules
trigger_conditions
trigger_actions
goals
dictionary_entries
resource_mappings
briefing_characters
missing_resource_members
referenced_missing_resources
latest_waypoint_eta_seconds
max_route_span_seconds
```

`exact` compares only the keys explicitly listed; it does not assert that no
other counter keys exist.

`latest_waypoint_eta_seconds` is the greatest numeric waypoint `ETA` in the
read-back mission. `max_route_span_seconds` is the greatest
`max(ETA) - min(ETA)` span among all group routes. Prefer route span for a
duration contract: it remains meaningful when a route's waypoint ETAs are not
monotonic, while the latest ETA is an elapsed offset from mission start.
The corresponding time of day is `mission.start_time + ETA` (with normal
day-boundary handling); that sum is not stored in `ETA`. Neither fact predicts
combat delays or actual play time. The coverage checker treats them as
separate observed facts, so a complete-profile contract must still assert both
when both are nonzero. Do not use time-of-day seconds as the latest ETA.

`required` tests set membership for:

```text
unit_types
payload_clsids
waypoint_actions
waypoint_task_ids
group_tasks
start_modes
airdrome_ids
briefing_fields
trigger_condition_predicates
trigger_action_predicates
goal_predicates
```

`airdrome_ids` values are numeric. The other required values are strings.
Recognized start-mode strings are `cold_parking`, `hot_parking`, `runway`,
`cold_ground`, `hot_ground`, `air`, and `other`.

`exact_values` checks any scalar in the read-back `mission` table. Each record
contains exactly a nonempty `path` array and finite scalar `value`. String path
segments select string Lua keys; numeric segments select numeric Lua keys:

```json
{
  "exact_values": [
    {"path": ["date", "Year"], "value": 1988},
    {"path": ["start_time"], "value": 50400},
    {
      "path": ["weather", "clouds", "preset"],
      "value": "RainyPreset1"
    },
    {"path": ["weather", "clouds", "base"], "value": 500},
    {
      "path": [
        "coalition", "red", "country", 1, "plane", "group", 1,
        "units", 1, "parking"
      ],
      "value": 12
    }
  ]
}
```

Paths are relative to `mission`; do not include a leading `"mission"` segment.
Duplicate paths, empty segments, tables as expected values, JSON `null`, and
non-finite numbers are rejected. Use these assertions for user-critical date,
time, weather, unit, parking, route, and trigger scalars in `mission`.
The `RainyPreset1` example uses a 500-metre cloud base; still query
`dcs-cloud-presets` for the exact preset ID and allowed range in the target
install rather than treating the example as universal.

### Group-bound role contracts

`expect.roles` binds user-visible scenario roles to exact group IDs. Every
record must contain all required fields shown here; role names and group IDs
must be unique. A linked FARP/ship start can additionally assert optional
`helipad_id` and `link_unit` fields.

```json
{
  "roles": [
    {
      "role": "player_interceptor_flight",
      "group_id": 101,
      "side": "red",
      "category": "plane",
      "group_task": "Intercept",
      "unit_types": {"EXACT_PLAYER_TYPE": 2},
      "human_slots": {"Player": 1, "Client": 0},
      "start_mode": "cold_parking",
      "airdrome_id": 23,
      "late_activation": false,
      "mission_elapsed_start_seconds": 0,
      "minimum_waypoints": 5,
      "minimum_route_span_seconds": 3600,
      "required_waypoint_task_ids": [
        "ComboTask",
        "AttackGroup"
      ],
      "required_waypoint_actions": [
        "From Parking Area",
        "Turning Point",
        "Landing"
      ],
      "required_task_group_ids": [301]
    }
  ]
}
```

The fields mean:

| Field | Check |
|---|---|
| `role` | Nonempty caller label, unique within the role list |
| `group_id` | Positive numeric DCS group ID resolving to one actual group |
| `side` | Exact `red`, `blue`, or `neutrals` coalition key |
| `category` | Exact `plane`, `helicopter`, `vehicle`, `ship`, or `static` |
| `group_task` | Exact group `task` string, or JSON `null` when the actual field is absent |
| `unit_types` | Exact per-type counts within this group |
| `human_slots` | Exactly both `Player` and `Client` keys with exact counts |
| `start_mode` | First-waypoint classification: `cold_parking`, `hot_parking`, `runway`, `cold_ground`, `hot_ground`, `air`, or `other` |
| `airdrome_id` | Exact numeric first-waypoint `airdromeId`, or JSON `null` |
| `helipad_id` | Optional exact numeric first-waypoint `helipadId`, or JSON `null`; include for a linked facility |
| `link_unit` | Optional exact numeric first-waypoint `linkUnit`, or JSON `null`; include for a linked facility |
| `late_activation` | Exact boolean derived from `lateActivation is true` |
| `mission_elapsed_start_seconds` | Optional exact nonnegative group `start_time` / first-waypoint `ETA`, measured from mission start, or JSON `null` when absent; complete-profile coverage requires the field for every role |
| `minimum_waypoints` | Minimum number of route points |
| `minimum_route_span_seconds` | Minimum `max(ETA) - min(ETA)` for this route |
| `required_waypoint_task_ids` | Unique nonempty task IDs that must occur anywhere in this group's route task tree |
| `required_waypoint_actions` | Unique nonempty waypoint `action` strings that must occur in this route |
| `required_task_group_ids` | Unique positive group IDs that must occur as `groupId` references anywhere in this route task tree |

Under `complete_scenario`, the set of group IDs in `expect.roles` must equal
the set of actual mission group IDs. Partial role coverage produces
`groups_not_fully_role_bound`, which is fatal to the quality gate. This makes
package roles, side/category/type counts, human slots, starts, route duration,
landing, activation, and target/escort links explicit instead of relying on
global totals alone.

Example contract fragment:

```json
{

    "theatre": "EXACT_INTERNAL_THEATRE",
    "mission_version": 23,
    "minimum": {

        "EXACT_PLAYER_TYPE": 2,

      },

      "payload_clsids": ["{EXACT-VERIFIED-CLSID}"],

```

Replace every placeholder with evidence. For a real request, cover all critical
user constraints expressible by the vocabulary. An empty contract provides no
scenario-preservation proof.

The build report also returns `contract.coverage_warnings`. These conservative
warnings identify common facts that the caller left out: theatre/version,
date/time/weather paths, exact group/unit/type and player-slot type counts, all
observed CLSIDs/actions/tasks/start modes/predicates/airfields/briefing fields,
trigger/goal/timeline scalars (including route span), full group-role coverage,
and explicit zero missing-resource assertions. Coverage warnings do not make an
undeclared user requirement known and do not change `contract_valid`. They are
review-only for `technical_fixture`, but fail the `complete_scenario` quality
gate; clear every one for a user-facing mission.

Zero trigger rules, conditions, actions, or goals always produce an
`*_absent` coverage warning. Consequently, a triggerless or goalless artifact
cannot report `validation.review_warnings_clear: true`, even if a sparse
contract explicitly accepts zero.

## Provenance and determinism

Recommended provenance shape:

```json
{
  "provenance": {
    "installed_dcs_version": "recorded version",
    "static_sources": ["relative source plus SHA-256"],
    "observed_registry": {
      "content_identity_returned": false,
      "filters": "exact filters",
      "coverage": "anonymous matching mission count"
    },
    "unresolved_runtime_checks": [
      "DCS mission load",
      "Mission Editor resave"
    ]
  }
}
```

The builder records `seed` but does not perform random generation. Determinism
comes from complete caller input, canonical data-only Lua serialization, fixed
archive timestamps and permissions, stable member order, and fixed compression
settings. Verification also rejects archive members not declared by the spec.
Identical specs and resources produce identical MIZ bytes.

## Commands

```powershell
python Tools\dcsmizzer.py build-miz spec.json output\mission.miz
python Tools\dcsmizzer.py verify-miz output\mission.miz --spec spec.json
```

`build-miz` refuses an existing output. `--force` intentionally replaces that
exact file. Read both JSON reports and require exit code 0. See
[validation.md](validation.md) for the meaning of each validation field.

`build-miz` and `verify-miz` open each resource once as a regular file, bind
its identity and initial SHA-256 to that handle, read only through the bound
handle, and recheck identity/content before completion. `verify-miz` therefore
requires every resource source file still to exist. A spec alone does not
embed binary-resource hashes.
